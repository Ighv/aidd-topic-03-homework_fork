# Задание №4. Новая функциональность: персональный мониторинг акций

## 1. Обоснование выбора

Вариант опирается на существующую модель `Share` и на фоновое обновление цен: не нужны
внешние сервисы, всё проверяется локально. Пользователь получает свой список наблюдения
и уведомления по достижении целевой цены.

## 2. Функциональные требования к новой функциональности

Сформулированы до реализации и использованы как чек-лист при проверке.

| ID | Требование |
|---|---|
| FR-N-01 | Авторизованный пользователь добавляет акцию в персональный список наблюдения. |
| FR-N-02 | Повторное добавление той же акции тем же пользователем не создаёт дубль. |
| FR-N-03 | Пользователь удаляет акцию из своего списка наблюдения. |
| FR-N-04 | Пользователь создаёт ценовое уведомление: акция, целевая цена, условие `above` (≥) или `below` (≤). |
| FR-N-05 | Уведомление срабатывает, когда последняя известная цена удовлетворяет условию. |
| FR-N-06 | Срабатывание фиксируется один раз, повторные проверки не дублируют его. |
| FR-N-07 | Неактивные и уже сработавшие уведомления не проверяются. |
| FR-N-08 | Пользователь видит свои уведомления и их состояние (активно, сработало, время). |
| FR-N-09 | Список наблюдения и уведомления доступны через REST API только для своих записей. |
| FR-N-10 | Неавторизованный пользователь не имеет доступа к страницам и API мониторинга. |

### Критерии приёмки

- Повторный запуск проверки не меняет `triggered_at` уже сработавшего уведомления.
- При `last_price = None` уведомление не срабатывает, задача не падает.
- Через API нельзя получить или создать запись другого пользователя.

## 3. Изменения в модели данных

Миграция `dashboard/migrations/0008_pricealert_watchlist.py`.

**Watchlist**

- `user` → `auth.User`, `CASCADE`, `related_name="watchlists"`
- `share` → `Share`, `CASCADE`, `related_name="watchlists"`
- `created_at`
- `unique_together = ("user", "share")` — закрывает FR-N-02

**PriceAlert**

- `user`, `share`
- `target_price` — целевая цена
- `condition` — `above` / `below`
- `is_active` — включено ли уведомление
- `triggered` — признак уже зафиксированного срабатывания
- `triggered_at` — время срабатывания
- `created_at`, сортировка `-created_at`

## 4. Изменения в архитектуре и интерфейсе

- **Веб-слой:** функции `watchlist_list`, `watchlist_add`, `watchlist_remove`,
  `alerts_list`, `alert_add`, `alert_remove` в `dashboard/views_ext.py`,
  все под `@login_required`, выборки ограничены `user=request.user`.
- **Маршруты:** `/watchlist/`, `/watchlist/add/`, `/watchlist/remove/<pk>/`,
  `/alerts/`, `/alerts/add/`, `/alerts/remove/<pk>/`.
- **Формы:** `WatchlistForm`, `PriceAlertForm` в `dashboard/forms.py`.
- **Шаблоны:** `watchlist.html`, `watchlist_form.html`, `watchlist_remove.html`,
  `alerts.html`, `alert_form.html`, `alert_remove.html`, ссылки в `base.html`.
- **API (DRF):** `WatchlistViewSet`, `PriceAlertViewSet` в `dashboard/api/v1/views_ext.py`,
  сериализаторы в `serializers_ext.py`, регистрация в `router.py` →
  `/api/v1/watchlist/`, `/api/v1/alerts/`; `IsAuthenticated` и фильтрация по `request.user`.
- **Фоновая задача:** `check_alerts` в `dashboard/tasks.py`, расписание `check-alerts`
  в `config/celery.py` с интервалом 10 секунд.

и уведомление, задача проверки запускается дважды, затем страницы и API запрашиваются
от имени этого пользователя.

## 6. Осознанные ограничения

- Уведомление фиксируется в БД и видно в интерфейсе и API; отправка e-mail/push не реализована.
- Источник цены — `Share.last_price`, который обновляет существующая задача `update_last_price`.
- Модели не зарегистрированы в админке: для варианта достаточно веб-интерфейса и API.
