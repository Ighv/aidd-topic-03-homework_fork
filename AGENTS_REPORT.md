# Отчёт (`cline`, второй)


## 1. Какие задачи ставились агенту

1. Анализ исходного кода по шести пунктам задания 1 → `ANALYSIS.md`.
2. Восстановление функциональных требований: FR, сценарии, бизнес-правила,
   перечень неоднозначностей и дефектов → раздел в `ANALYSIS.md`.
3. Технический аудит, исправление дефектов, рефакторинг, запуск приложения,
   автоматические тесты → `MODERNIZATION.md` + код.
4. Новая функциональность, вариант «Персональный мониторинг акций»:
   список наблюдения, целевые цены, уведомления без дублей → `NEW_FEATURE.md` + код.

Задания 3 и 4 велись раздельно: сначала только исправления, коммит,
затем новая функциональность отдельным коммитом.

## 3. Ошибки и проблемы при работе с агентом

    Django 4.1 и Celery 5.2 несовместимы с Python 3.14: падение
  на импорте, агент сначала предложил понижать версию Python. Принят вариант
  с SQLite вместо незапущенного PostgreSQL и правкой `SECRET_KEY`/`ALLOWED_HOSTS`.
    В первой версии `ANALYSIS.md` не было
  сценариев пользователя, а по заданиям 3–4 отсутствовали отдельные документы —
  агент посчитал анализ достаточным и остановился.
    Повторное добавление бумаги в watchlist давало
  500 вместо идемпотентного ответа: `unique_together` не был обработан, агент
  этого не проверил.
    `@login_required` уводил на `/accounts/login/`, которого
  в проекте нет, — страницы мониторинга отдавали 302 вместо 200.
    Агент не учёл, что цена и свечи приходят в nano-единицах;
  пустой ответ API обрабатывался как ошибка, а не как «данных нет».
    Работа шла на бесплатной модели: несколько раз ловился отказ по
  частоте запросов, после чего приходилось ждать и повторять шаг. Длинные
  команды в терминале иногда приходили с битым JSON аргументов, и вызов
  инструмента не выполнялся — помогало дробление на короткие команды.

## 4. Какие корректировки вносились

    Дописаны сценарии пользователя, созданы `MODERNIZATION.md` и `NEW_FEATURE.md`
  с требованием: отдельный документ на каждое задание.
    Дубль watchlist закрыт `get_or_create` и валидацией в сериализаторе API,
  добавлен тест на повторное добавление.
    Добавлен `LOGIN_URL`, путь входа приведён к существующему `/user/login/`,
  проверка страниц повторена под авторизованным пользователем.
    Проверка уведомлений вынесена в отдельный сервис, чтобы тестировать её без
  Celery и без брокера.
    Пересчёт nano-единиц и обработка пустого ответа вынесены в явные ветки кода.
    После каждого отказа по лимиту задача дробилась на более мелкие шаги.

## 5. Как проверялись результаты


`python manage.py check` — ошибок нет.
`python manage.py migrate` — миграции применяются, включая `0008`.
`python manage.py test` — все тесты проходят (число см. в таблице сравнения).
`GET /` и `GET /api/v1/shares/` — 200 без авторизации.
    `/watchlist/`, `/alerts/` под входом — 200; без входа — редирект на рабочий
  `/user/login/`.
    API мониторинга под двумя разными пользователями — каждый видит только свои
  записи.
    Срабатывание уведомления и подавление повторов — проверено на БД: после
  повторного прогона задачи новой записи не появляется.
    Требования из `ANALYSIS.md` сверены с кодом построчно; дефекты из списка
  проверены на наличие исправления.

## 6. Время и итерации

Анализ и требования — 2 итерации: чтение кода и первый вариант `ANALYSIS.md`,
затем дописывание сценариев и FR со ссылками на файлы.

Окружение — 2 итерации: диагностика несовместимости Django 4.1 и Celery 5.2 с
Python 3.14, затем переход на SQLite и правка настроек.

Модернизация и дефекты — 3 итерации: аудит зависимостей, исправление дефектов
реализации, отдельный проход по рефакторингу и `MODERNIZATION.md`.

Новая функциональность — 4 итерации: модели и миграция `0008`, страницы и API,
периодическая задача, исправление дублей watchlist и тесты.

Итого около часа календарного времени и примерно 11 итераций. Основное время ушло на
окружение и проверки, а не на генерацию кода: во втором проходе уже был известен
обход несовместимости Django 4.1 с Python 3.14, поэтому этап настройка прошла быстрее
